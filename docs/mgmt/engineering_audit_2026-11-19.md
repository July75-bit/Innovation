# 工程审计与重构建议（2026-11-19）

> 触发：用户反馈「赛程要能点开看选手并进入购买」+「夜间模式排序下拉还是白底」，并要求按第一性原理、
> 二阶影响、跨领域、红队、Git 历史、新人认知成本、30 天 PR/CI、30 天 Bug 返工十条线索一起审视。
>
> 数据来源：本仓库 `git log`（截至 `a9e2c2d`）、GitHub Actions API（172 次运行）、GitHub PR API、
> `AGENTS.md` 事故记录、前端源码实测。**所有数字可复算**，口径写在每节里。

## 0. 结论先行

1. 「下拉白底」不是样式漏写，而是**全站没有声明 CSS `color-scheme`**：原生控件跟平台走，不跟我们的变量走。
   修根层 + 加守卫，才是"一次修完所有同类问题"的解。
2. 「赛程补全」的本质不是缺一个页面，而是**"看到某场比赛 → 看到人 → 去买"这条路径断了**。
   用右侧抽屉（quick view）补最薄的一环：赛程仍轻，深度操作交回详情页。
3. 项目真正的成本大头不在代码复杂度，而在**文档/演示材料的多渠道数字同步**与**没有合并护栏的直推流程**：
   近 30 天 397 个提交里 120 个是 docs、129 个是 merge；churn 前 15 名里 12 个是文档。
4. 设计系统叠加了 4 代（深色 → 液态玻璃 → 令牌 v2 → 纸感），留下的历史层仍全局加载，
   新人需要理解 3 套并存的名字才能改样式。
5. 可立即回收的复杂度：`CollapsibleCard.vue`（0 引用）、`liquid-glass.css`/`ui-kit.css` 全局导入（仅演示页/浮层用）、
   `UiTable/UiNav/UiPagination` 等只在 `/ui-kit` 出场的展示组件、`--glass-*` 中已无效的高光/边缘令牌。

## 1. 需求重定义：症状、原因与更值得解决的问题

| 用户表述 | 症状 | 我们判断的底层需求 | 是否误把手段当目标 |
| --- | --- | --- | --- |
| 排序下拉夜间还是白色 | 单个控件白底 | **主题能力缺失**：原生控件配色没有根层声明，也没有防回归检查 | 是。只改这个 `select` 会漏掉日期控件/滚动条/自动填充/未来新控件 |
| 赛程每天对战要能点开 | 赛程页只显示对阵 | **缩短"发现选手 → 决策 → 交易"的路径**，而不是"再加一个页面" | 有可能。独立比赛页也能点开，但多一次跳转，且 28 轮 × 4 人的信息密度不值得一个完整页面 |
| 补全赛程内容 | 页面信息薄 | 让赛程页承担"赛前侦察"职责：谁在这场上、现在什么价、值不值得看 | 否，但要注意别把交易也搬进来（职责膨胀） |

**更值得解决的问题（本轮顺手做的）**：主题能力与守卫、赛程-选手数据路径、以及原先"未知路径静默重定向"
（已在 11-18 改成 404）这类"看起来正常、实际在骗用户"的交互。

## 2. 三个方案（赛程）与取舍

| 方案 | 交互 | 优点 | 代价 / 风险 | 结论 |
| --- | --- | --- | --- | --- |
| **A. 行内展开**（最早我也是这么想的） | 点行 → 行下方展开 4 张卡 | 上下文最强、实现最轻、无遮罩 | 28 行列表高度剧烈抖动；展开后要滚动才能看全；移动端更难 | 否 |
| **B. 右侧抽屉**（用户选择，已实现） | 点行 → 右侧 quick view | 保持列表可见；移动端可全宽；成熟模式（交易所/电商 quick view） | 引入 API 懒加载；小屏遮挡列表；需处理焦点/滚动锁 | **是** |
| **C. 独立比赛详情页** | `/matches/:round` | 可收藏/分享/深链；适合外部引用 | 新增路由 + 404 + 状态同步；28 个页面价值不足；演示时多一跳 | 否（可作为后续） |

**为什么 B 是当前最优**：信息量只有 4 人、操作只有"看行情"，属于"浏览上下文里的轻详情"；
C 的成本（路由/分享/状态）与收益不匹配；A 会让列表失去稳定感（与纸感"从容"冲突）。

## 3. 二阶、三阶影响

1. **赛程页从"纯静态"变成"静态 + 懒加载"**：原页面离线可用，现在点开抽屉会请求 `/api/players`。
   处理：懒加载（点开才请求）+ 成功缓存 + 失败给重试且不影响赛程本身；赛程主体仍零依赖。
2. **"点行"语义叠加**：原来点行只切换轮次，现在同时切轮次 + 开抽屉。
   处理：保留 chip/翻页作为纯浏览路径；关闭抽屉后仍停在选中轮次，符合"我看了这轮"的预期。
3. **未来 28 轮全部可看**：会提前暴露"下一场谁上场"，但本项目无真实对手/无博彩，用户已确认可接受；
   若未来接入真实赛事，可加"未来轮次只显示对阵、不显示名单"的开关（现在不需要）。
4. **移动端**：420px 抽屉在 390 屏等于全屏，用户会短暂失去列表上下文；可接受（关闭即回），
   但若后续要频繁对比多场，建议改底部 sheet + 保留 40vh 列表。
5. **可访问性**：行加了 `tabindex/role=button`、Enter/Space 可开；抽屉 `role=dialog`、Esc/遮罩关闭、
   焦点落关闭按钮、body 滚动锁。副作用：自动 focus 会出现红色焦点环（截图里那个红圈），这是**正确的焦点可见**，不是 bug。
6. **组件复用**：抽屉里的"选手精简卡"将来可被"持仓页/赛程页/搜索"复用；先内联，出现第二处再抽。

## 4. 跨领域参照

- **交易终端**：行情表格双击 → 侧栏下单面板（保持列表，操作在侧栏）——与本方案同构。
- **电商 quick view**：列表页点商品 → 右侧/弹层快速查看，完整详情另开页——本方案即此模式。
- **GitHub Issues**：点 issue → 右侧/独立页，列表保留过滤状态——我们刚做的"返回保留状态"同源。
- **音乐 App**：列表 → 底部 now playing，不离开列表——移动端可借鉴的下一步。
结论：**"列表 + 轻详情侧栏 + 深操作跳页"**是跨行业验证过的分层，不是特例。

## 5. 红队：假设 B 是错的

| 反方论点 | 证据 | 重新评估 |
| --- | --- | --- |
| 赛程页本来不依赖后端，加 API 会破坏答辩容错（后端冷启动 1 分钟） | 演示时后端若未预热，点球员会转圈/失败 | 已降级：失败只影响抽屉并给重试；赛程主体全程可用；答辩前 `prewarm.py` 仍是 P0 |
| 抽屉在手机上遮挡全部内容，等于跳转，却比跳转更贵 | 390px 实测抽屉 = 全屏 | 可接受但非最优；后续可改底部 sheet（保留列表 40vh） |
| 行点击同时切轮 + 开抽屉，会打扰只想翻轮次的用户 | 保留 chip/左右翻页作为替代路径 | 可接受；若用户反馈烦，可改为"点行只开抽屉、不同步轮次"（一行开关） |
| 未来轮次显示名单 = 泄露排兵 | 用户确认可接受；无真实对手 | 保留，加开关成本很低（后置） |
| 抽屉里放"看行情"多一跳，用户想要就地买 | 就地买会引入交易校验/余额/停牌规则，赛程页职责膨胀 | 维持跳详情；详情页已有完整交易面板与 AI 建议 |

**没有找到推翻 B 的硬证据**；A/C 在特定场景（超多选手、需要分享）更优，但当前数据量不支持。

- 前端 `src` 约 **1.6 万行**；最大 5 个文件：`ScheduleView.vue` 1498、`PlayerDetailView.vue` 1359、
  `MarketView.vue` 1100、`App.vue` 931、`AuthView.vue` 815（含大量内联 `<style scoped>`）。
- 命名不直观示例：`lede`（简报总述）、`hl`（重点数字条）、`p-card`（选手卡）、`quiet-link`、
  `sheet`（抽屉）、`glass--panel`（实色面板）、`UiNav` vs 业务侧栏。

  1. 新增 `docs/software/ARCHITECTURE.md`（一页：目录职责、数据流、四代术语对照、改样式的正确入口）；
  2. 删除 `CollapsibleCard.vue`；把 `/ui-kit` 相关 CSS 改为路由级异步 import；
  3. 给大 SFC 设"软阈值"（>800 行拆子组件/样式文件），ScheduleView/PlayerDetailView 优先；
  4. 统一命名表（`lede→brief-summary`、`hl→highlight`、`p-card→player-card`），一次性机械替换 + 测试；
  5. 在 README 顶部加"10 分钟跑起来 + 5 分钟看懂结构"。

## 8. 近 30 天 PR / CI 分析

- **PR 只有 1 个**：`#3 Develop`（2026-10-23，创建到合并 **2m43s**）。日常是**直接推 develop**，没有 PR 评审。
- **CI 共 172 次运行**（workflow：`.github/workflows/ci.yml`）；近期时长 **49–82 秒**（#165 71s、#166 49s、#171 65s、#172 82s）。
  慢因是"后端测试 + 前端 lint/build/test"全套跑一遍，绝对值不高，不构成瓶颈。
- 真正浪费的是**重复触发**：129 个 merge 提交同样触发 CI（合并本身很少改语义）。
  建议：`git pull --rebase` 代替 merge（能消掉 83 个 "Merge branch develop into develop"），
  或至少在合并提交上跳过全量测试、只跑冒烟。
- **护栏缺失**：CI 没有"冲突标记"检查（历史上两次把 `<<<<<<<` 推上去导致前端构建失败）。
  建议在 CI 加一行 `git grep -n "^<<<<<<< " && exit 1`（成本 1 行，收益最高）。

## 9. 近 30 天 Bug / 返工 / 回滚复盘

| 事件 | 直接原因 | 共同根因 |
| --- | --- | --- |
| 两次冲突标记进仓库（CI/部署挂） | 手工解冲突后 `git add -A` | **R5 合并流程无护栏** |
| 浅色登录页"白底白字" | AuthView 硬编码深色时代的颜色 | **R2 主题靠组件自觉，缺根层与守卫** |
| 夜间排序下拉白底（本轮） | 从未声明 `color-scheme` | **R2**（同一根因，第二次发作） |
| 模型 JSON 透传到页面 | `summary[:80]` 直接展示 | **R1 展示层信任外部文本** |
| 手机端表格被压扁 | 桌面表格硬套窄屏 | 缺"响应式验收"清单 |
| 对比度审计误报（4.41 判违规） | 选择器穿透到子组件 | 缺少"作用域选择器"规则 |
| 改选择器后 4 个测试连环失败 | 测试断言 DOM class（duck typing） | **R3 测试与 CSS 选择器耦合** |
| 文档数字反复漂移（216/231/276/308…） | 测试数/覆盖率在 6+ 个文件重复手写 | **R4 文档数字多源复制** |
| 改 MarketView 时脚本截断丢 `</script>` | 注释里含字面 `<template>` | 缺少"改大文件用行锚点"的约定 |
| 白屏 TDZ（`watch` 在 `useRoute` 之前） | setup 执行顺序 | 缺少 App 级冒烟（已补） |

**可沉淀的规则（按投入产出排序）**

1. **主题能力守卫**（本轮已落地 `theme-guards.spec.ts`）：`color-scheme` + 原生控件 + 禁止硬编码黑白。
2. **CI 冲突标记检查**：一行 grep，消灭最高频的"低级但致命"事故。
3. **测试断言语义化**：优先 `data-testid` / 可访问角色，不直接绑 class（改版少返工）。
4. **数字单一来源**：测试数/覆盖率由脚本从 pytest/vitest 输出生成一段 markdown，再被各文档引用；
   避免"改代码后手工改 8 处文档"。
5. **大文件阈值**：>800 行 SFC 不再内联新增样式；新交互先抽 composable/子组件再写。
6. **外部文本统一清洗入口**：模型/后端文本进入 UI 前必须经 `clean*` 函数（后端 + 前端各一层）。
7. **pull --rebase + 小步提交**：减少 merge 与冲突，CI 运行次数预计可降 20–30%。
