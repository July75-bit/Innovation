# 答辩问答准备（5 分钟 · 20% 分）

> **负责人**：D 汇总，全员认领 ｜ **用法**：每题背 2–3 句，**先给结论再给证据**；答不上就说"这一版没做，原因是…"，不要编。
> **覆盖**：合规 / 定价 / AI / 并发与数据 / 测试与质量 / 部署 / 团队与反思 七类，共 **18 问**。

## 一、合规与定位（高频，必背）

**Q1 这算不算赌博？**
不是。全程**虚拟币**，不可充值、不可提现、不可兑换任何实物或服务；没有真实资金通道，价格是我们自己设的模拟数据。定位是课程作品、模拟交易教学演示。
（证据：README 合规声明、`compliance.md` §1、页面页脚）

**Q2 那如果要做成真产品，需要什么？**
金融牌照、KYC、反洗钱、资金托管与监管备案——目前**完全不涉及**。我们不打算也不能把它做成真产品。

**Q3 用了选手的真实姓名和战队，合规吗？**
只用了**公开可查的职业身份信息**（姓名/战队/位置，来自公开榜单），不使用任何隐私数据；价格和评分明确标注为模拟；不展示任何官方图片或 Logo，与 Valve、HLTV、俱乐部**无关联**。
（证据：`compliance.md` §1/§4、`data/seed_players.json` 的声明字段）

## 二、定价机制（最容易被追问）

**Q4 价格公式是什么？为什么这么设计？**
`P' = max(floor, P × (1 + αS + βD))`，α=0.15、β=0（本期不用需求项）、floor=1.0、单次涨跌对称 clamp ±20%。选乘性更新是因为"涨跌按比例"更符合价格直觉，`max(floor, …)` 保证不会跌成 0 或负数。

**Q5 S 是怎么算的？为什么除以 3？**
先算本轮得分相对近 5 场均值的 z-score，再 `S = clamp(z/3, -1, 1)`，即 3σ 记满格。**如果直接用 z，1σ 就满格**（约 32% 的场次顶格），价格会二值跳动；除以 3 之后只有真正的爆发/崩盘才满格，α 的语义也固定成"满格 = ±15%"。评审若要字面口径，把 `Z_FULL_SCALE` 设为 1.0 即可（有测试守着这个开关）。

**Q6 我们测出价格长期温和下行，是 bug 吗？**
不是 bug，是机制特性，而且我们**主动写进了报告**：100 个 seed × 30 轮，区间收益中位数 −7.40%。根因两条：① 得分在 100 处截断，高分段（5 人 base rating ≥80）右尾被削平 → `E[S]` 略小于 0；② 乘性更新的波动拖累。两者都正比于 α，α 调小（0.08/0.05）下行明显收敛，报告里有对比表。

**Q7 价格变化能追溯吗？答辩问"这条价格为什么动"你怎么答？**
能。每条 `price_history.reason` 强制带 `S` 和本轮得分，例：`本场表现下滑（S=-1.00），价格下跌 15.00%（本轮得分 76.6）`。这是"方案 A"决策：不新增 score 列/不建 matches 表，把归因写进 reason，不改表也不改契约。（`test_price_reason_traceability.py` 4 条守着）

**Q8 为什么不用机器学习预测价格？**
6 天工期 + 无真实赛事数据，ML 只会得到"看似高级但不可解释"的结果。我们对"可解释"的要求高于"准"：老师/用户要能问"为什么动"，公式能当场手算。回测里规则版的**回撤显著低于买入持有**（5.9% vs 14.9%）。

## 三、AI 智能体

**Q9 AI 到底做了什么？是不是只是调了个 API？**
四层：① `build_player_context` 把行情、持仓、最近价格点拼成上下文（查库失败回落 seed）；② 固定 6 字段 JSON 契约；③ 失败降级规则版；④ 回测对比规则版 vs 随机 vs 买入持有。我们**明确把它定位成"建议者"而非"决策者"**：AI 永不改余额，调用前后账户逐字节一致（有测试）。

**Q10 AI 挂了怎么办？**
无密钥 / 超时（20s）/ 非 JSON / 枚举非法 → **一律 HTTP 200 + `source=rule_fallback`**，返回同样 6 字段，交易完全不受影响。AI 故障不用 4xx/5xx，这是我们写进契约的硬规则。"AI 挂了也能交易"本身可以当演示点。

**Q11 怎么保证 AI 不乱说？**
三道：契约（6 字段 + 枚举校验，非法就降级）、规则兜底（阈值明确可解释）、只读（不写库）。前端只按 `source` 区分展示，不做二次判断。
**局限**：我们没有 LLM 版回测数据（无密钥），报告里如实写了"待补"。

## 四、并发与数据

**Q12 两个人同时买同一支，会超卖吗？**
不会。判断写在 SQL 的 `WHERE` 里（`UPDATE … WHERE balance >= :amount`），靠 `rowcount` 判断是否命中，失败即整体回滚。**上线前我们真的踩过这个坑**：先查后写导致 5000 变 5504、凭空多卖一股（BUG-01），修复后并发两笔"卖 1"→ `[200, 400]`，只入账一次。

**Q13 为什么不用 `SELECT … FOR UPDATE`？**
SQLite 会**静默忽略** `FOR UPDATE`（编译出的 SQL 里干脆没有），本地测试全绿、线上才生效——这是最危险的"本地好线上炸"。我们选方言中立的"条件更新 + rowcount"，SQLite 和 Postgres 行为一致。

**Q14 金额精度怎么保证？**
数据库层 `NUMERIC(12,2)`；应用层全程 `Decimal` 计算，**禁止 SQL 端 `SUM()` 聚合**（SQLite 把 NUMERIC 存成 REAL，SQL 端求和会出分位误差，Postgres 不会 → 会变成"本地线上算得不一样"）。

## 五、测试与质量

**Q15 测试做了什么？**
**120 条**（单元 107 / 集成 13），CI（ubuntu）与本机（Windows）都全绿；核心逻辑覆盖率 **91%**（课程要求 ≥60%）。按层分：交易边界 14 条、并发 3 条、定价 11 条、同 seed 复现 3 条、AI 13+6+7 条、异常矩阵 7 条、recalc 5 条。
（证据：`test_report.md` §1/§2、`test_plan.md` TC-001~122）

**Q16 发现了什么真实缺陷？**
10 条全记录、全修复、每条带可复跑用例，其中 2 个 P0：**并发超卖**（5000→5504）、**部署阻断**（SQLAlchemy 2.1 起裸 `postgresql://` 默认驱动是 psycopg3，项目只装 psycopg2 → Render 起不来）。还有"reason 得分双写""清仓写 0 触发 CHECK 报 500"等。

**Q17 有没有没做到的？**
有，我们如实写：① **外部交叉原型测试没约到组**（问卷 12 问已就绪，`cross_test.md` §4 写了延期原因与补救）；② LLM 版回测未跑（无密钥）；③ 无移动端适配与完整无障碍（键盘可达性不足，已列为 P0 待修）；④ 无并发压测（6 天不够）。

## 六、部署

**Q18 线上怎么部署的？数据会丢吗？**
Render Blueprint 三个服务：前端 Static Site + 后端 Web Service + **Postgres 18**。免费实例没有持久盘，所以**必须**用 Postgres——我们实测过：重新部署后端后，交易流水仍 3 条、价格点仍 11 个，一条没丢（TC-404）。
已知限制：免费库 **2026-11-23 到期**；实例 15 分钟无流量休眠，冷启动约 1 分钟（演示前预热）。已验证：health / CORS / 买卖闭环 / 持久化 / 子路由刷新 / 无密钥可用（TC-401~406 全 ✅）。

## 七、团队与反思（收尾加分）

**Q19 四个人怎么分工的？有人划水吗？**
按**写权限边界**分：A 前端、B 后端与部署、C 定价引擎、D AI/测试/质量/文档；跨边界改动要对方确认。每人都有可查的提交记录与产物（如 C 的 `pricing_model.md` §7 回测、A 的 16 张真机验收图）。协调方式：每日站会 + `milestones.md` 看板 + GitHub Issues/Milestones 三件套。

**Q20 如果重做，你会改什么？**
三件：① **先冻结接口契约再写代码**（这次契约改了字段，前端返工）；② 把"价格长期下行"这类机制特性**在文档前移**（这次是回测才发现，属于验证太晚）；③ 把外部交叉测试排进第 2 天而不是拖到第 5 天（越晚越难约）。

## 附：3 个"救命句式"

- 被问到没做的东西：「这一版没做，原因是 X；如果要做，第一步会是 Y。」
- 被问到数字细节：「这个数字在 `test_report.md` 第 6 节 / `pricing_model.md` 第 7 节有完整记录，我可以现场打开。」
- 被问倒了：「这个我不能确定，回去查证后回复。」——**不要编**，编一个错数字比说不知道扣分更多。
